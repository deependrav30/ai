# AI-Powered Customer Support & Incident Management System
## Detailed Requirement Specification

---

## 1. Purpose

This document defines the **complete functional, non-functional, technical, and agentic requirements** for building an **AI-driven collaborative customer support and incident management platform**.

The system is **not a traditional chatbot**.  
It behaves like a **mini support organization powered by multiple collaborating AI agents**, with:
- Planning and delegation
- Retrieval-Augmented Generation (RAG)
- Persistent memory
- Explainable reasoning
- Guardrails and safe escalation
- Full observability

This document is intentionally written to be **clear enough for AI agents or engineers to directly generate production-grade code**.

---

## 2. High-Level Business Scenario

### 2.1 User Representation (No Authentication Scope)

Authentication and authorization are **out of scope** for this implementation.

Instead, the UI will expose **three tabs** representing user roles:

| Tab | Description |
|---|---|
| Customer | End user raising issues via chatbot |
| Employee | Support and operations dashboard |
| Admin | System training and configuration |

---

## 3. Incident Type & Priority (AI-Driven)

### 3.1 Auto Classification (Mandatory)

- **Incident type and priority must NOT be manually selected**
- Both are **auto-generated by an AI Classification Agent**
- Classification is based on:
  - User intent
  - Detected keywords
  - Historical incident patterns
  - Business rules

---

### 3.2 Priority Mapping Rules (Initial Assumptions)

| Incident Category | Priority |
|---|---|
| Payment-related issues | P0 |
| System UI dashboard blocker | P0 |
| Loan amount change | P1 |
| Password change | P2 |

> These rules are **seed rules**.  
> The AI agent may refine classification using historical data and context.

---

## 4. Admin Requirements (Training & Knowledge Management)

### 4.1 Admin Responsibilities

Admin is responsible for **training and configuring the system** by uploading knowledge artifacts used by AI agents.

---

### 4.2 Document Upload Capabilities

Admin can upload:
- Company details
- Process documents
- Historical incident reports
- Runbooks and SOPs

#### Supported File Types
- PDF (multi-page)
- Word (`.docx`)
- PowerPoint (`.pptx`)
- Text (`.txt`)
- Images (OCR required)

> Documents may contain **images with embedded text**, which must also be indexed.

---

### 4.3 Storage Rules

- No S3 or cloud storage
- Files stored locally under:

/data/uploaded/


Recommended structure:

/data/uploaded/{type}/{subtype}/{priority}/


---

### 4.4 Metadata Captured per Document

| Field | Description |
|---|---|
| Type | Company / Process / Incident |
| Subtype | Payments / KYC / Loans / UI etc |
| Priority | P0 / P1 / P2 / P3 |
| Uploaded By | Admin |
| Timestamp | Auto-generated |

---

### 4.5 Knowledge Indexing (Mandatory)

- Documents must be chunked
- Chunk overlap must be applied
- Chunk size and overlap must be configurable
- Vector indexing required
- Metadata must be preserved for explainability

This forms the **Semantic Memory** of the system.

---

## 5. Customer Requirements (Chatbot & Sessions)

### 5.1 Customer Selection

- Customer selects a **sample customer** from a dropdown
- Data sourced from `customer` table in DB
- No login flow

---

### 5.2 Chatbot Session Management

#### Session Rules
- Every chat = unique session
- Session context must be stored
- Context isolation is mandatory

#### Context Behavior

| Scenario | Context Rule |
|---|---|
| Same session | Full context retained (up to max limit) |
| New session (same customer) | Partial summarized context |
| Different customer | No shared context |

Context growth must be controlled using:
- Windowing
- Summarization
- Pruning

---

## 6. Agent-Based Request Handling

### 6.1 Planner / Orchestrator (Mandatory)

Every customer request:
1. Goes to **Ingestion Agent**
2. Routed to **Planner / Orchestrator Agent**
3. Planner decides:
   - Which agents to invoke
   - Execution order (serial / parallel / async)
   - Whether human escalation is needed

---

## 7. Customer Use Case Flows

---

### 7.1 Password Change (P2)

**Handled by: Password Change Agent**

Flow:
1. Ask verification method:
   - OTP (static OTP = `123456`)
   - OR old password
2. Validate input
3. Ask new password twice
4. If both match:
   - Update password in customer DB
5. Confirm success

> Fully AI-handled. No human involvement.

---

### 7.2 Gold / Silver ETF Purchase (P0 – Payment)

**Handled by: Payment Agent**

Flow:
1. Customer selects ETF type (Gold / Silver)
2. Select company
3. Display current price
4. Customer chooses:
   - Amount OR grams
5. Select payment method:
   - UPI ID OR dummy QR scanner
6. Simulate payment success
7. Generate dummy transaction ID
8. Provide:
   - Receipt download link
   - Email confirmation (dummy)

---

### 7.3 Payment Failure / Money Debited (P0)

**Handled by: Reasoning & Correlation Agent**

Scenarios:
- Payment not working
- Payment failed
- Money debited but no confirmation

Flow:
1. Analyze issue
2. Retrieve historical payment incidents
3. Correlate patterns
4. Suggest resolution
5. If confidence low or customer dissatisfied:
   - Escalate to human agent

---

### 7.4 KYC Issues

Flow:
1. Collect basic details
2. Ask customer to:
   - Turn on video
   - Record verification
   - Show ID proof
   - Provide signature
3. Capture recording
4. Assign to **physical human agent** for verification

---

### 7.5 Loan Inquiry / Loan Amount Change (P1)

Flow:
- Capture request
- Auto-assign to **Credit Manager (Human)**
- No AI resolution attempt

## 8. Employee Requirements (Operations Dashboard)

### 8.1 Incident Visibility

Employees must see **all incidents** with complete traceability.

Each incident must display:

| Field | Description |
|---|---|
| Incident ID | Unique |
| Customer | Reference |
| Status | Open / In Progress / Resolved / Escalated |
| Priority | Auto-generated (P0–P3) |
| AI Agents Involved | Names |
| AI Suggestions | Text |
| Tools Used | Retrieval, Memory, Policy |
| Reasoning Trace | Decision explanation |
| Final Outcome | Resolved / Assigned |
| Assigned Human | If escalated |

---

### 8.2 AI Transparency

Employees and AI agents can see:
- Which agents ran
- What data was used
- Why a decision was made

---

## 9. Mandatory Agent Architecture

Each agent must exist in a **separate module/file**.

### Required Agents

- Ingestion Agent
- Planner / Orchestrator Agent
- Intent & Classification Agent
- Knowledge Retrieval (RAG) Agent
- Memory Agent
- Reasoning / Correlation Agent
- Response Synthesis Agent
- Guardrails & Policy Agent

---

## 10. Memory Model

### 10.1 Memory Types

| Memory Type | Purpose |
|---|---|
| Working Memory | Current task context |
| Episodic Memory | Past incidents & chats |
| Semantic Memory | Documents & KB |

---

### 10.2 Memory Persistence

- Memory must persist across requests
- Past interactions influence future decisions
- UI must allow humans to:
  - View memory
  - Modify memory
  - Delete memory

---

## 11. RAG Requirements (Non-Negotiable)

- Retrieval must occur **before generation**
- Strict separation of:
  - Retrieval
  - Reasoning
  - Response synthesis
- Retrieved content must be referenced
- Index at least:
  - 100 documents
  - Each document 5–6 pages minimum

---

## 12. Guardrails & Safety

Guardrails Agent must:
- Prevent violence
- Prevent self-harm
- Prevent sexual content
- Prevent hate speech
- Prevent jailbreak attempts

Actions:
- Respond with “I don’t know”
- Or escalate safely to human agent

---

## 13. Execution Model

System must demonstrate:

| Mode | Description |
|---|---|
| Serial | Dependent agent flow |
| Parallel | Independent agent execution |
| Async | Memory & observability updates |

## 14. Observability & UI

UI must:
- Live stream agent execution

A **real-world-ready AI-powered support system** that:
- Thinks like a coordinated team
- Explains its decisions
- Learns from history
- Escalates responsibly
- Is observable, debuggable, and safe
